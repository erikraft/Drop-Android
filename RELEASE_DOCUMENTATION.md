# ErikrafT Drop™ for Android — Release & Signing Documentation

This document explains how to configure, sign, build, and publish ErikrafT Drop™ for Android both locally and in a CI/CD environment (GitHub Actions).

---

## 1. Google Play App Signing & Key Strategy

When publishing on Google Play, Google uses two types of signing keys:
1. **Upload Key**: Used by developers to sign `.aab` (Android App Bundle) files before uploading them to the Google Play Console.
2. **App Signing Key**: The actual production private key used by Google to sign the final `.apk` files delivered to user devices. Google generates or receives this key when the app is first registered and stores it in Google's secure infrastructure.

The Android App Bundle (AAB) generated by our Release Pipeline is signed with the configured **Upload Key** (defined by the `KEYSTORE_FILE` secret). Google Play Console verifies this signature upon upload, extracts the assets, and then signs the final device-specific APK with the **App Signing Key**.

> ⚠️ **IMPORTANT**:
> - Never upload the App Signing Key (production key) to Google Play as an upload key.
> - Never commit your `.jks`, `.keystore`, `.p12`, or any other private key files to Git.

## 2. GitHub Secrets and Protected Environment Configuration

To run the automated GitHub Actions release pipeline successfully, you must configure four repository secrets in your GitHub repository and link them to a protected Environment.

### How to configure a protected Environment and repository secrets:
1. On GitHub, navigate to your repository's landing page.
2. Click on **Settings** in the top navigation bar.
3. In the left sidebar, click on **Environments**.
4. Click on **New environment** and name it **`production`**.
5. (Optional but highly recommended) Under **Environment protection rules**, check **Required reviewers** and specify the reviewers who must approve any production release before the build starts.
6. Under **Environment secrets**, click on **Add secret** to add each of the following four secrets:

| Secret Name | Description |
|---|---|
| `KEYSTORE_FILE` | The entire binary Keystore (`.jks`) file encoded as a Base64 string. |
| `KEYSTORE_PASSWORD` | The password of your Keystore. |
| `KEY_ALIAS` | The alias of your private key within the Keystore. |
| `KEY_PASSWORD` | The specific password of your private key within the Keystore. |

### How to generate `KEYSTORE_FILE` (Base64 representation):
You can convert your local `.jks` or `.keystore` file to a Base64 string by running one of the following commands:

* **Linux / macOS:**
  ```bash
  base64 < my-release-key.jks | tr -d '\n'
  ```

* **Windows PowerShell:**
  ```powershell
  [Convert]::ToBase64String([IO.File]::ReadAllBytes("my-release-key.jks"))
  ```

Copy the generated Base64 text and paste it into the value field of `KEYSTORE_FILE` on GitHub.

## 3. How to Build Locally

To build a Release build locally, you must provide your signing configuration. This is supported via **environment variables** or a **`keystore.properties`** file.

### Method A: Environment Variables
Run the build commands with the environment variables set:

* **Linux / macOS:**
  ```bash
  export KEYSTORE_PATH="/path/to/my-release-key.jks"
  export KEYSTORE_PASSWORD="your-keystore-password"
  export KEY_ALIAS="your-key-alias"
  export KEY_PASSWORD="your-key-password"

  ./gradlew clean assembleRelease bundleRelease
  ```

* **Windows PowerShell:**
  ```powershell
  $env:KEYSTORE_PATH="C:\path\to\my-release-key.jks"
  $env:KEYSTORE_PASSWORD="your-keystore-password"
  $env:KEY_ALIAS="your-key-alias"
  $env:KEY_PASSWORD="your-key-password"

  ./gradlew clean assembleRelease bundleRelease
  ```

### Method B: `keystore.properties` File
Alternatively, you can create a `keystore.properties` file in the root directory of the project (this file is already ignored in `.gitignore`):

```properties
storeFile=/path/to/my-release-key.jks
storePassword=your-keystore-password
keyAlias=your-key-alias
keyPassword=your-key-password
```

Then run:
```bash
./gradlew clean assembleRelease bundleRelease
```

## 4. Safe Versioning Mechanism

Never generate two Google Play Store releases with the same `versionCode`.

To safely update the version of your app prior to creating a tag/release:
1. Open `app/build.gradle`.
2. Locate the `defaultConfig` block:
   ```groovy
   versionCode 16
   versionName "9.0.7"
   ```
3. Increment the integer value of `versionCode` by at least 1 (e.g., `versionCode 17`).
4. Update the `versionName` string value (e.g., `versionName "9.1.0"`).
5. Commit and push these changes to your master/main branch before tagging.

## 5. Automated Pipeline Release Workflow

Once the environment and secrets are configured, creating a new production release is simple:

1. Update the version inside `app/build.gradle` (see Section 4).
2. Tag your commit with the release version:
   ```bash
   git tag v9.1.0
   git push origin v9.1.0
   ```
3. The **Signed APK + AAB Release Pipeline** will automatically trigger, validate the tag against the `versionName` inside `app/build.gradle`, run tests, and then request approval/execution on the protected **production** environment. Upon approval, it will build the signed artifacts, verify the signatures, upload the files as Actions artifacts, and create a GitHub Release containing:
   - `ErikrafT-Drop-v9.1.0.apk`
   - `ErikrafT-Drop-v9.1.0.aab`
