# Optical-transfer and GitHub-directory audit

This document records the implementation boundary for the Android client. It is deliberately
conservative: a coloured matrix that cannot decode the Cimbar wire format is **not** presented as
Cimbar support.

## Current Android implementation (audited from source)

* `MainActivity` owns the WebView, installs `JavaScriptInterface` as
  `ErikrafTdropAndroid`, and routes WebView downloads through the hardened native streaming path.
  The app's normal peer transfer remains WebRTC/WebSocket based and is not modified here.
* `JavaScriptInterface` creates the destination before receiving WebView chunks, serializes writes,
  validates the final byte count, and deletes an incomplete target. It is the required integration
  point for any future WebView-to-native archive transfer.
* `qr/QRTransferActivity`, `QREncoder`, `QRDecoder`, `ErikrafTQRProtocol`, and `FountainFEC`
  implement the existing offline **ERIKRAFT-QR / Animated QR** feature. Its protocol uses per-frame
  CRC32 and final SHA-256 validation; the FEC implementation is two-source XOR parity, not a
  general fountain-code implementation.
* The QR receiver uses the Android camera permission and the legacy Camera API. This change stops
  the preview when the activity enters the background and restarts only on resume, preventing
  background camera capture/decoding.
* `OnionTransferActivity` and `TorController` are separate from optical transfer. No Tor callback,
  proxy, WebRTC, WebSocket, download, or WebView bridge code was altered.

## Cimbar / CFC decision

No Cimbar, libcimbar, CFC, OpenCV, NDK, WebAssembly, images, or source code is bundled by this
change. Consequently there is no unreviewed MPL-2.0 native dependency, ABI/APK-size increase, or
claim of visual-only compatibility. The cited Cimbar commit is MIT, but CFC's documented
`libcimbar` dependency is MPL-2.0 and its complete dependency graph must be audited before an
encoder/decoder is embedded.

A real Cimbar implementation must be delivered with protocol fixtures generated by the exact
pinned upstream version, automated encode/decode tests, physical camera tests (rotation,
perspective, exposure, blur, duplicate/lost/reordered frames), and retained third-party notices.
It must also introduce an explicit `LegacyQRTransfer` / `CimbarOpticalTransfer` boundary rather
than changing ERIKRAFT-QR frames.

### Interoperability status at this revision

| Direction | Status | Reason |
| --- | --- | --- |
| Cimbar -> Drop | NOT SUPPORTED | No Cimbar decoder is bundled or tested. |
| Drop -> Cimbar | NOT SUPPORTED | Drop does not generate Cimbar frames. |
| Cimbar -> CFC | NOT SUPPORTED (by Drop) | Outside this application's protocol; no end-to-end fixture run was performed. |
| Drop -> CFC | NOT SUPPORTED | Drop does not generate CFC/Cimbar-compatible frames. |
| CFC -> Drop | NOT SUPPORTED | No CFC/Cimbar decoder is bundled. |
| ERIKRAFT-QR <-> Drop | SUPPORTED | Existing offline animated-QR implementation remains unchanged. |

## GitHub folder URL safety foundation

`GitHubDirectoryUrl` accepts only canonical public URLs in the form
`https://github.com/OWNER/REPOSITORY/tree/BRANCH/path`. It rejects alternate hosts, cleartext,
credentials, query/fragment tokens, encoded separators, traversal segments, and a missing folder.
It performs no network I/O and never handles a GitHub token.

A subsequent downloader must resolve the parsed public repository through the GitHub API, stream
individual files into `ZipOutputStream`, use the Storage Access Framework/MediaStore destination,
and expose cancellation and foreground lifecycle state. It must not use this parser's output as an
arbitrary URL, load an archive into memory, or infer slash-containing branch names: GitHub's tree
URL is ambiguous in that case and needs API-backed ref resolution.
